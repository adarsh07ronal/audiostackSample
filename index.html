hal.py — Hardware Abstraction Layer

Class

Purpose: Wraps a WAV file and exposes it as a hardware audio source. Guarantees that every read() call returns exactly the requested number of bytes — it loops and pads with silence when the file ends. This is how real audio HALs behave: the downstream pipeline must never receive a short buffer.

Imports

ImportWhy
import waveStandard library — opens .wav files and reads their PCM data + metadata (channels, sample rate, sample width)

Class: AudioHAL

class AudioHAL
Abstracts a WAV file behind a hardware-neutral read interface. Caller never touches the file object directly.

Constructor

def __init__(self, filepath: str)
Opens the WAV file with wave.open(filepath, 'rb'). Stores the file handle as self._wf. No audio data is read yet.
def __init__(self, filepath):
    self._wf = wave.open(filepath, 'rb')   # 'rb' = read binary

Methods

def get_params(self) → tuple(nchannels, sampwidth, framerate)
Returns the WAV file's audio parameters. Used by main.py to configure the PyAudio output stream to match the source format.
def get_params(self):
    return (
        self._wf.getnchannels(),  # int — 1=mono, 2=stereo
        self._wf.getsampwidth(), # int — bytes per sample (2 = 16-bit)
        self._wf.getframerate()  # int — samples per second, e.g. 44100
    )
def read(self, nframes: int) → bytes
Core method. Reads nframes PCM frames. If the file is exhausted, seeks back to frame 0 (looping) and continues reading. Pads with \x00 bytes (digital silence) if even looping can't fill the buffer.
def read(self, nframes):
    channels, sampwidth, _ = self.get_params()
    expected = nframes * channels * sampwidth  # total bytes required
    data = b''
    max_loops = 5  # CONSTANT — safety guard against infinite loop

    # ── LOOP: keep reading until buffer is full ──
    for _ in range(max_loops):
        chunk = self._wf.readframes(nframes)
        data += chunk
        if len(data) >= expected:
            break
        self._wf.rewind()  # seek to frame 0 on EOF

    # ── PADDING: silence-pad if still short ──
    if len(data) < expected:
        data += b'\x00' * (expected - len(data))

    return data[:expected]  # trim to exact size

Key Constants (inside read)

NameValueMeaning
max_loops5Maximum rewind attempts before giving up and padding. Prevents infinite loop on a corrupt or zero-length WAV.
expectednframes × channels × sampwidthThe exact byte count the caller expects. Buffer contract.
💡 Why silence padding?

Audio hardware DMA (Direct Memory Access) fills a ring buffer in fixed-size slots. If you hand it a short buffer it can either crash, glitch, or block. Padding with \x00 = digital silence (int16 value 0) is safe and industry standard.

mixer.py — PCM Audio Mixer

Functions + Constant

Purpose: Takes three PCM byte streams and a set of weights, mixes them in floating-point space to avoid integer overflow, normalises the gain, clips, then returns the result as int16 PCM bytes.

Imports

ImportWhy
import numpy as npVectorised float32 operations on the entire buffer at once — far faster than a Python for-loop over 1024 samples

Module-level Constant

CHUNK: int = 1024
Number of audio frames processed per cycle. Determines latency: smaller = lower latency, higher CPU cost. 1024 frames at 44100 Hz = ~23 ms per chunk. Mirrors ALSA's period size concept.

Functions

def to_array(data: bytes, channels: int = 1, sampwidth: int = 2) → np.ndarray
Converts raw PCM bytes into a NumPy integer array. Selects np.int16 for 2-byte samples (16-bit), np.int32 for 4-byte (32-bit). Used internally by mix3.
def to_array(data, channels=1, sampwidth=2):
    dtype = np.int16 if sampwidth == 2 else np.int32
    return np.frombuffer(data, dtype=dtype)
    # np.frombuffer — zero-copy view into the bytes object
def mix3(m, n, c, wm, wn, wc, channels=1, sampwidth=2) → bytes
The core mixer. Converts three PCM byte streams to float32 arrays, applies weights, normalises if total gain > 1, clips to int16 range, returns bytes.
def mix3(m, n, c, wm, wn, wc, channels=1, sampwidth=2):

    # ── STEP 1: bytes → float32 arrays ──
    a1 = to_array(m, channels, sampwidth).astype(np.float32)
    a2 = to_array(n, channels, sampwidth).astype(np.float32)
    a3 = to_array(c, channels, sampwidth).astype(np.float32)

    # ── STEP 2: align to shortest (critical safety fix) ──
    min_len = min(len(a1), len(a2), len(a3))
    a1, a2, a3 = a1[:min_len], a2[:min_len], a3[:min_len]

    # ── STEP 3: weighted sum ──
    out = a1 * wm + a2 * wn + a3 * wc

    # ── STEP 4: normalise gain ──
    total = wm + wn + wc
    if total > 1.0:
        out = out / total       # prevent amplification above full scale

    # ── STEP 5: clip + convert back to int16 bytes ──
    out = np.clip(out, -32768, 32767)
    return out.astype(np.int16).tobytes()

Type Reference

ParameterTypeRangeMeaning
m, n, cbytes—Raw PCM bytes for music, nav, call streams
wm, wn, wcfloat0.0 – 1.0Volume weight per stream
channelsint1 or 2Mono or stereo

🔥 Why float32?

int16 max is 32767. If you add two int16 samples at full scale: 32767 + 32767 = 65534 — this overflows an int16 and wraps to −2 (catastrophic distortion). float32 has a 32-bit mantissa so intermediate values stay accurate. You only clip back to int16 at the very end.

router.py — Audio Router

Class + State Machine

Purpose: Maintains the current audio mode (music / nav / call) and returns the correct mixing weights for each frame. Simulates what Android AudioFocus / AAOS audio policy does: grant or deny focus to each audio stream based on priority.

Class: AudioRouter

class AudioRouter
A finite state machine with 3 states: "music", "nav", "call". State transitions are driven by a frame counter.
def __init__(self)
Sets self.mode = "music". The default state — music plays until an event triggers a transition.
def update_mode(self, frame_idx: int) → None
State transition function. Uses integer range checks on frame_idx to simulate timed audio events. Mutates self.mode.
def update_mode(self, i):
    # ── CONDITIONAL: frame-based state machine ──
    if   50  <= i < 150:  self.mode = "nav"
    elif 200 <= i < 350:  self.mode = "call"
    else:                  self.mode = "music"
def get_weights(self) → tuple[float, float, float]
Maps current mode to mixer weights. Returns (wm, wn, wc). This is the Strategy pattern — the behaviour (weights) changes based on the current mode without any if/else in the caller.
def get_weights(self):
    if   self.mode == "call":  return (0.0, 0.0, 1.0)
    elif self.mode == "nav":   return (0.3, 1.0, 0.0)
    else:                       return (1.0, 0.0, 0.0)
    # call > nav > music  (priority hierarchy)

main.py — Entry Point (PyAudio)

Main loop

Purpose: Wires all modules together. Opens PyAudio output, runs 1000 iterations of the mixing loop, handles cleanup. This is the main event loop — analogous to Android's AudioFlinger mixing thread.

Imports

ImportWhy
import pyaudioOpens system audio output stream (PortAudio backend)
from hal import AudioHALWAV-file hardware abstraction
from mixer import mix3, CHUNKWeighted PCM mixer + buffer size constant
from router import AudioRouterPriority-based mode/weight manager

Constants (runtime)

NameValueMeaning
CHUNK1024 (from mixer.py)Frames per iteration
channelsfrom music HALAudio channel count (1 or 2)
sampwidthfrom music HAL (2)2 bytes = 16-bit samples
ratefrom music HAL (e.g. 16000)Sample rate in Hz
EXPECTEDCHUNK × channels × sampwidthRequired output bytes per chunk

Main loop

# ── SETUP ──────────────────────────────────────
music_hal = AudioHAL('streams/music_16.wav')
nav_hal   = AudioHAL('streams/nav_16.wav')
call_hal  = AudioHAL('streams/call_16.wav')
router    = AudioRouter()
pa        = pyaudio.PyAudio()

channels, sampwidth, rate = music_hal.get_params()
EXPECTED = CHUNK * channels * sampwidth

stream = pa.open(
    format=pa.get_format_from_width(sampwidth),
    channels=channels, rate=rate, output=True
)

# ── MAIN LOOP: 1000 iterations ─────────────────
try:
    for i in range(1000):
        # 1. Read CHUNK frames from each HAL
        m = music_hal.read(CHUNK)
        n = nav_hal.read(CHUNK)
        c = call_hal.read(CHUNK)

        # 2. Update router state (state machine tick)
        router.update_mode(i)
        wm, wn, wc = router.get_weights()

        # 3. Mix three streams into one
        out = mix3(m, n, c, wm, wn, wc, channels, sampwidth)

        # 4. Safety: enforce exact buffer size
        if len(out) != EXPECTED:
            if len(out) < EXPECTED:
                out += b'\x00' * (EXPECTED - len(out))
            else:
                out = out[:EXPECTED]

        # 5. Write to audio device
        stream.write(out)

finally:
    stream.stop_stream()
    stream.close()
    pa.terminate()
⚠️ try/finally resource management

PyAudio opens a system resource (audio device). If the loop throws (e.g. KeyboardInterrupt), finally ensures the stream is always closed. Leaking a PyAudio instance can lock the audio device on some systems.

ℹ️ S16_LE

Signed 16-bit Little-Endian PCM. The standard format for audio on x86 Linux systems. Little-endian means the least significant byte comes first in memory — matching x86 native byte order, so no byte-swapping overhead.

Concepts & Design Patterns

Every pattern used in this codebase maps directly to patterns used in production automotive audio stacks.

🏗️ Hardware Abstraction Layer (HAL)

Structural

The AudioHAL class hides the fact that audio comes from a WAV file. The caller (main.py) only calls hal.read(n) and hal.get_params() — it doesn't know or care whether the source is a file, a microphone, Bluetooth, or a network stream.

In production: Android defines IStreamIn and IStreamOut HAL interfaces. Every audio chip vendor (Qualcomm, MediaTek) implements these. The AudioFlinger mixer never touches hardware directly.

Analogy

Like a USB port — your laptop doesn't care if a mouse, keyboard, or hard drive is plugged in. The USB protocol (HAL interface) is fixed; the device behind it varies.

🎯 Strategy Pattern

Behavioural

AudioRouter.get_weights() returns different weight tuples based on self.mode. The mixer (mix3) doesn't contain any mode logic — it just uses whatever weights it receives. The strategy (weight policy) is decoupled from the execution (mixing).

In production: Android AudioPolicyManager uses a similar strategy: it evaluates usage, content type, and flags to produce a routing decision, then hands it to AudioFlinger.

Analogy

Like a GPS giving directions — your car just follows the turn instructions. The car doesn't know if the GPS is routing around traffic, taking the scenic route, or avoiding toll roads.

🔄 Finite State Machine

Behavioural

update_mode(i) is a classic FSM: it has a set of states (music, nav, call) and a transition function driven by the frame index. Only one state is active at a time.

# FSM transition table
i < 50       → music
50 ≤ i < 150  → nav
150 ≤ i < 200 → music
200 ≤ i < 350 → call
i ≥ 350       → music

In production: Android AudioFocus is an FSM. Transitions: GAIN → LOSS → LOSS_TRANSIENT → LOSS_TRANSIENT_CAN_DUCK → GAIN.

📦 Layered Architecture

Structural

Each layer only communicates with the layer directly above or below it:

  • hal.py — reads hardware (or file)
  • router.py — decides policy
  • mixer.py — executes math
  • main.py — orchestrates

This is the OSI model applied to audio. Swap any layer without touching the others.

🔒 Buffer Contract / Invariant

Safety

Both hal.py and main.py enforce that every buffer is exactly CHUNK × channels × sampwidth bytes. This is a class invariant — a guarantee that must hold at every call boundary.

Why: Audio hardware uses ring buffers. If you write fewer bytes than the hardware period size, you'll get an underrun (glitch). If you write more, you'll overwrite the next period.

Analogy

Like ATM cash cassettes — they hold exactly 100 notes. Whether it's dollars or blanks (silence), the cassette must be full before the machine will accept it.

🌊 Floating-Point Domain Mixing

Signal Processing

Converting int16 → float32 before arithmetic, then clipping back to int16 at the end is called fixed-to-float-to-fixed conversion. It prevents integer overflow during intermediate calculations.

In production: Android AudioFlinger internally operates in 32-bit or 64-bit float. Hardware output is only quantised to int16/int24 at the very last stage (the HAL write call).

🎚️ Audio Ducking

Domain

Reducing a stream's volume (not muting) to make room for another. In nav mode: wm = 0.3 (music at 30%) while wn = 1.0 (nav at full). The user can still hear music faintly.

In production: AudioManager.AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK — apps should lower volume but keep playing. Used for navigation prompts, notifications, and turn-by-turn.

♻️ RAII / try-finally

Safety

The PyAudio stream is opened before the loop and closed in a finally block. This is RAII (Resource Acquisition Is Initialization) — the resource lifetime matches the code block, not an arbitrary point where cleanup might be forgotten.

Equivalent patterns: Python's with statement, C++ destructors, Java try-with-resources, Rust's Drop trait.

AAOS (Android Automotive OS) Audio

Audio Usage Types

AAOS extends Android with automotive-specific audio usages in AudioAttributes:

  • USAGE_MEDIA — music, podcasts
  • USAGE_ASSISTANCE_NAVIGATION_GUIDANCE — nav prompts
  • USAGE_VOICE_COMMUNICATION — phone calls
  • USAGE_SAFETY — collision warning (highest priority)
  • USAGE_EMERGENCY — overrides everything

Audio Zones

AAOS supports multiple audio zones in the car (driver, passenger, rear seat). Each zone has its own volume, focus, and output device:

  • Primary zone — driver's display & speakers
  • Rear zone — rear entertainment screen
  • Zones can play different content simultaneously
  • This project simulates a single zone

PCM Audio Fundamentals

Sample Rate

How many samples per second. Common values:

  • 16000 Hz — voice/telephony (this project)
  • 44100 Hz — CD quality
  • 48000 Hz — professional / HDMI

Nyquist theorem: max reproducible frequency = sample_rate / 2.

Bit Depth

Bits per sample = dynamic range.

  • 16-bit — 65536 levels, 96 dB range (this project)
  • 24-bit — 16.7M levels, 144 dB range
  • 32-bit float — used internally by mixers

Latency Budget

End-to-end latency sources:

  • Buffer size: 1024 frames @ 44100 Hz = 23 ms
  • HAL buffer: adds 10–20 ms
  • DSP processing: 5–10 ms
  • Total target < 100 ms (perceptible: > 250 ms)

Ring Buffer (how real audio hardware works)

The Ring Buffer Concept

Audio hardware uses a circular (ring) buffer in DMA memory. The CPU writes chunks (periods) into the ring, and the hardware reads them continuously at the sample rate. If the CPU is late (underrun), the hardware reads stale data → audible glitch (pop/crackle).

  • Period size = chunk the CPU writes at a time (= CHUNK = 1024)
  • Buffer size = total ring size (= 2-4 × period)
  • Underrun = CPU wrote too slowly → glitch
  • Overrun = CPU wrote too fast → overwrote unplayed data
Ring buffer (4 periods):
[ period 0 ][ period 1 ][ period 2 ][ period 3 ]
↑ HW reads ↑ CPU writes

When HW pointer catches CPU → underrun!
HAL pads with zeros → silence > glitch

Hardware components in a real car head-unit

🎛️ LPASS (Low Power Audio SubSystem)

A dedicated audio DSP block inside Qualcomm Snapdragon automotive SoCs. Handles mixing, echo cancellation, noise reduction, and equalisation in hardware — offloading the main CPU. This project's mixer.py runs on the main CPU instead.

🔊 Audio Codec Chip

Converts digital PCM (from LPASS) to analogue voltage (DAC) and drives the speaker amplifier. Examples: Qualcomm WCD938x, Texas Instruments TAS5825. This project uses PyAudio → system soundcard → built-in DAC.

📡 Bluetooth Audio (A2DP)

Phone music streams over Bluetooth A2DP → decoded by the head-unit → fed into LPASS as a PCM stream. The HAL presents it identically to a local file. This project simulates it with music_16.wav.

🎙️ Acoustic Echo Cancellation (AEC)

During a phone call, the speaker plays call audio while the microphone picks up the caller's voice. AEC removes the echo (speaker → mic feedback). This project has no microphone — call audio is played one-way only.

Interview Prep

Common questions on audio stacks, embedded systems, Android audio, and signal processing — with answers grounded in this project.

Low-Level Audio Concepts

What is PCM?

Pulse Code Modulation. The standard way to represent audio digitally. At each time step (1/sample_rate), the amplitude of the analogue signal is measured and quantised to the nearest integer value.

A 16-bit, 44100 Hz, mono, 1-second audio file = 44100 × 2 = 88,200 bytes.

Analogy

Like a flip-book animation: many still frames (samples) played rapidly enough appear as smooth motion (sound).

What is a buffer underrun?

Audio hardware reads from a ring buffer at a fixed rate. If the software doesn't refill it fast enough, the hardware reads stale or zero data — causing a pop, crackle, or silence gap.

In this project: hal.py pads with b'\x00' (silence) to prevent the caller from ever getting a short buffer. main.py also pads the mixer output before writing to PyAudio.

Why convert to float32 before mixing?

int16 range: −32768 to 32767. Adding two max-amplitude int16 values: 32767 + 32767 = 65534 — overflows int16 (wraps to −2). float32 has 32-bit mantissa; intermediate values stay accurate. Clip back to int16 only at the very end.

What is audio ducking?

Reducing (not muting) one stream's volume to make a higher-priority stream audible. Example: navigation prompt at 100% volume, background music reduced to 30%.

Android: AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK tells apps to duck. Apps that don't duck get their focus revoked.

What is a HAL?

Hardware Abstraction Layer. A standardised interface that separates OS/framework code from hardware-specific code. The framework calls the HAL interface; the vendor implements it for their chip.

Android HAL types: Legacy C HAL → HIDL (Binder-based) → AIDL (current). This project's Python class is a simplified HAL: same concept, no IPC.

What is ALSA?

Advanced Linux Sound Architecture — the kernel-level audio subsystem on Linux. It exposes audio devices as /dev/snd/pcmC0D0p files. PyAudio talks to PortAudio which talks to ALSA.

main_alsa.py skips PortAudio and calls ALSA directly via alsaaudio — one fewer abstraction layer.

Q&A — Click to reveal answers

How does AudioFlinger mix multiple streams in Android? ▼

AudioFlinger's MixerThread runs a tight loop (similar to main.py's for-loop). Each iteration it reads a period of PCM from every active AudioTrack's ring buffer, applies per-track volume and effects, sums them (like mix3), and writes the result to the HAL output stream.

Key difference from this project: AudioFlinger uses fixed-point 4.28 arithmetic (not float32) for performance on low-power SoCs. Modern LPASS hardware can offload mixing entirely from the ARM CPU.

What is AudioPolicyManager and how does it differ from AudioFlinger? ▼

AudioPolicyManager = the brain. It decides where audio goes (routing) and who gets to play (focus). It reads audio policy configuration XML and applies rules. This project's router.py is a simplified AudioPolicyManager.

AudioFlinger = the hands. It actually mixes and outputs PCM data. It does what the policy says. This project's mixer.py + main.py's loop is a simplified AudioFlinger.

They communicate over Binder IPC. AudioPolicyManager tells AudioFlinger which output device and volume to use; AudioFlinger does the mixing.

What is the Nyquist–Shannon sampling theorem? ▼

To accurately represent a signal of frequency f, you must sample at ≥ 2f Hz (the Nyquist rate). Human hearing tops out at ~20 kHz, so CD audio at 44,100 Hz captures up to 22,050 Hz — more than enough.

This project uses 16,000 Hz sample rate (enough for voice: 300 Hz – 3.4 kHz telephone bandwidth). Sampling below Nyquist causes aliasing — high frequencies fold back and appear as low-frequency artefacts.

What is the difference between latency and throughput in audio? ▼

Latency: time from audio event to output. Critical for phone calls (<150 ms round-trip feels natural), gaming (<20 ms), and voice assistants. Reduced by using smaller buffers (lower CHUNK value). Trade-off: more CPU wake-ups.

Throughput: bytes per second of PCM data. Always fixed: sample_rate × channels × sampwidth. For 44100 Hz mono 16-bit = 88,200 bytes/sec. Not adjustable — must match hardware.

How would you add a 4th audio stream (e.g. rear-seat entertainment) to this project? ▼

1. Add a 4th HAL: rear_hal = AudioHAL('streams/rear.wav')

2. Extend mix3 to mix4(m, n, c, r, wm, wn, wc, wr) — add a 4th array and weight.

3. Add rear mode rules to AudioRouter.get_weights() returning a 4-tuple.

4. In main.py read the 4th stream each iteration and pass it to mix4.

In real AAOS: you'd create a second audio zone with its own output device, volume group, and focus stack. The rear zone is completely independent from the driver zone.

Why does hal.py loop/rewind the WAV file instead of just reading to EOF? ▼

The main loop runs 1000 iterations. Each iteration reads CHUNK frames. If the WAV files are shorter than 1000 × CHUNK frames, readframes() returns fewer bytes than requested.

The downstream pipeline (PyAudio write) expects exactly EXPECTED bytes. A short write would either crash PyAudio or cause an underrun. Looping the file simulates an infinitely long audio source — just like a streaming music service or live microphone.

What design pattern does router.py implement, and why is it useful? ▼

Strategy pattern (for get_weights) + Finite State Machine (for update_mode).

Strategy: the mixer doesn't contain any mode logic. You can change the routing policy (weights) without touching mixer.py. In production, AudioPolicyManager is loaded from a config XML — different car models can have different policies without recompiling AudioFlinger.

FSM: audio mode is a discrete state. Only one mode is active at a time. Transitions are well-defined. This makes the behaviour predictable, testable, and easy to extend with new states (e.g. "mute-all for safety alert").

Explain np.clip(out, -32768, 32767) — what happens without it? ▼

After the weighted sum, values might exceed the int16 range (e.g. if two streams both have weight 0.7 but happen to have identical phase). Without clipping:

astype(np.int16) uses C-style truncation: 33000 in int16 wraps to 33000 - 65536 = −32536. This is clipping distortion — extreme high-amplitude samples suddenly become large-negative values. You hear a sharp crack or heavy distortion.

Clipping to [−32768, 32767] before conversion causes soft saturation instead — the waveform is "flattened" at the peaks but doesn't wrap, so the distortion is much less severe.
